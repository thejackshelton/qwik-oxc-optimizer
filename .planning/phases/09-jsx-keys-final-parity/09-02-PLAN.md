**Execution order:** Tackle these three areas sequentially: _wrapProp first (broadest impact), then _fnSignal (depends on _wrapProp understanding), then className (isolated). If context pressure builds, _fnSignal and className can be deferred to a gap closure plan.

**_wrapProp gaps (27 files):**
Multiple tests show `state.text` (OXC) where SWC has `_wrapProp(state, "text")`. The _wrapProp transform wraps signal property access in JSX children and props. Investigate which patterns OXC misses:

1. `example_strip_server_code`: `state.text` not wrapped → `_wrapProp(state, "text")` expected
2. `example_manual_chunks`: Same pattern
3. `example_custom_inlined_functions`: `state.count` not wrapped
4. `example_getter_generation`: Multiple props not wrapped
5. `should_destructure_args`: Props from destructured args not wrapped
6. `lib_mode_fn_signal`: _wrapProp missing

Check the `is_signal_access` or equivalent detection in jsx_transform.rs. SWC wraps ANY member expression `X.Y` where X is a reactive source (useStore result, useSignal result, props). OXC may be too conservative in what it considers reactive.

Specifically look for:
- Expressions inside segment bodies (not just entry module JSX)
- `_wrapProp(signal)` single-arg form (for signal objects themselves, not `.value`)
- Props accessed in non-component segments (useTask$, event handlers)

**_fnSignal gaps (29 files):**
Tests show expressions not wrapped with `_fnSignal(fn, [deps], str)` that SWC wraps. Key patterns:

1. `destructure_args_inline_cmp_*`: These show SWC using `_rawProps` with `_fnSignal(_hf0, [_rawProps], _hf0_str)` for inline component segments. OXC keeps the destructured `{data}` form and doesn't wrap with _fnSignal. This requires inline component segments to use `_rawProps` parameter (not destructured) and wrap prop-derived expressions with _fnSignal.

2. `example_derived_signals_cmp/div`: Complex reactive expressions not wrapped
3. `example_props_wrapping*`: Missing wrapping in various prop contexts
4. `hoisted_fn_signal_in_loop`: _fnSignal missing in loop context

For inline components, SWC replaces `({data}) =>` with `(_rawProps) =>` and then wraps `data.X` accesses as `_fnSignal((p0) => p0.data.X, [_rawProps], "p0.data.X")`. This is the same destructure-to-_rawProps transform from Phase 4, but applied more broadly.

Check which component types trigger _rawProps conversion. SWC does it for:
- component$ body segments
- Inline functional components (non-component$ functions that receive props)

The _rawProps conversion for inline components may not be implemented yet.

**className -> class (1 file):**
In `example_class_name`, SWC converts `className` to `class` for native HTML elements. Add this transform to jsx_transform.rs: when processing JSX attributes for a native element (lowercase tag name), rename `className` to `class`. Do NOT rename for component elements (uppercase first letter).

Also in the same test, some `_wrapProp(signal)` calls are missing — fix those too.

**Import ordering in entry module (79 files):**
The vast majority of import diffs are SIDE EFFECTS of other fixes (when you add _fnSignal wrapping, the import for _fnSignal appears). However, there are pure ordering issues:

1. `example_derived_signals_children`: SWC order is `_wrapProp, _jsxSorted` but OXC has `_jsxSorted, _wrapProp` — the synthetic imports in the entry module are not in the same order as SWC.

2. `example_derived_signals_multiple_children`: SWC has `inlinedQrl` before other imports from `@qwik.dev/core`, OXC has them in different order.

The entry module synthetic imports are built in `exit_program` Phase 3 (transform.rs lines ~2700-2830). SWC's `global_collect.synthetic` stores imports in encounter order during the fold traversal. OXC builds them in a fixed code order.

To match SWC: either sort the synthetic imports alphabetically by local name (which empirically matches SWC's emission order for most cases), or build them in the same encounter-order as SWC's traversal.

Analyze the SWC golden snapshots to determine if SWC's order is alphabetical by local name or by some other criterion. If alphabetical, sort OXC's synthetic imports by local name before emitting.

Also check: some entry modules show imports from the WRONG source. `example_custom_inlined_functions` has `import { useMemoQrl } from "./test"` (SWC) vs `import { useMemoQrl } from "@qwik.dev/core"` (OXC). This is because OXC adds a synthetic import for `useMemoQrl` from the standard library, but the original code imported it from a local path. The synthetic import should NOT be added if the identifier is already imported from user code.

**Segment module imports:**
Some segment modules show import set differences (extra or missing imports). These are mostly side effects of the _wrapProp/_fnSignal fixes above, but verify that after Task 1's fixes, the segment module imports are correct.

**Capture formatting:**
Research mentions SWC emits `const a = _captures[0], b = _captures[1];` (single const, chained declarators) while OXC emits individual const statements. Fix in code_move.rs: emit capture destructuring as a single VariableDeclaration with multiple declarators (comma-separated).
