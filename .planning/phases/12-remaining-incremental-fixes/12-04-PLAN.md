  <name>Task 1: Bypass is_any_dep_used_as_object for destructured prop deps</name>
  <files>crates/qwik-optimizer-oxc/src/jsx_transform.rs</files>
  <action>
The root cause: when `collect_reactive_deps` detects a bare identifier like `fromProps` as a
destructured prop alias, it pushes `_rawProps` as the dep root_name. But `is_any_dep_used_as_object`
then checks if literal `_rawProps` appears as an object in the expression — it doesn't, because
the expression still contains `fromProps`.

In SWC's flow, the body rewrite happens BEFORE JSX transform, so by the time signal wrapping
runs, the expression is `_rawProps.fromProps + fromLocal`, and `_rawProps` IS used as an object.
In OXC's bottom-up flow, signal wrapping runs BEFORE body rewrite, so the expression still
has `fromProps`.

Fix: In BOTH the props path (around line 2296) and children path (around line 3096), after
`collect_reactive_deps` returns deps and before the `is_any_dep_used_as_object` check, detect
if any dep has root_name `_rawProps` AND that dep came from destructured prop alias detection
(i.e., destructured_props is Some and not empty). If so, bypass the `is_any_dep_used_as_object`
check entirely and proceed directly to wrapping.

The logic: when `_rawProps` is a dep, it means a destructured prop alias like `fromProps` was
found. After body rewriting, this becomes `_rawProps.fromProps`, which IS a member expression
with `_rawProps` as object. So we can safely skip the check.

Specifically, add a helper variable before the `is_any_dep_used_as_object` call:

```rust
let has_destructured_raw_props = destructured_props
    .map(|props| !props.is_empty())
    .unwrap_or(false)
    && deps.iter().any(|d| d.root_name == "_rawProps");
```

Then change the condition from:
```rust
if is_any_dep_used_as_object(&value, &dep_names) {
```
to:
```rust
if has_destructured_raw_props || is_any_dep_used_as_object(&value, &dep_names) {
```

Apply this same pattern to BOTH:
1. Props path (~line 2296)
2. Children path (~line 3096)

<task type="auto">
  <name>Task 2: Fix object property key replacement in _fnSignal body string</name>
  <files>crates/qwik-optimizer-oxc/src/jsx_transform.rs</files>
  <action>
The `replace_identifier_in_code` function (around line 1582) does naive text replacement
that also replaces object property KEYS, not just values.

Example: `{props: props.fromProps}` with replacement `props` -> `p0` becomes
`{p0: p0.fromProps}` instead of `{props: p0.fromProps}`.

The SWC expected output keeps the key intact: `{props: p0.fromProps}`.

Fix `replace_identifier_in_code` to skip replacements at object key positions. The function
does text-based replacement, so we need a heuristic to detect object key context.

Strategy: When a match is found, check if the character AFTER the match (after any whitespace)
is `:` AND the character BEFORE the match (ignoring whitespace) is one of `{`, `,`, or newline.
If both conditions are true, this is an object key position — skip the replacement.

More specifically, after finding a match at position `i`:
1. Look at what comes after the match: scan from `i + old_len` past whitespace. If the next
   non-whitespace char is `:` (but NOT `::` for scope resolution), this MIGHT be a key position.
2. Look at what comes before: scan backwards from `i - 1` past whitespace. If the previous
   non-whitespace char is `{`, `,`, or is at the start of the string, this IS a key position.
3. If both conditions match, skip the replacement.

Edge case: shorthand `{props}` (no colon) — this should NOT be skipped since the identifier
IS the value too. The colon check naturally handles this since shorthand has no `:`.

Implementation:
```rust
fn replace_identifier_in_code(code: &str, old_name: &str, new_name: &str) -> String {
    let mut result = String::with_capacity(code.len());
    let chars: Vec<char> = code.chars().collect();
    let old_chars: Vec<char> = old_name.chars().collect();
    let old_len = old_chars.len();
    let mut i = 0;

    while i < chars.len() {
        if i + old_len <= chars.len() && &chars[i..i + old_len] == old_chars.as_slice() {
            // Check word boundaries
            let before_ok = i == 0 || !is_ident_char(chars[i - 1]);
            let after_ok = i + old_len >= chars.len() || !is_ident_char(chars[i + old_len]);

            if before_ok && after_ok {
                // Check if this is an object property KEY position (skip replacement)
                if is_object_key_position(&chars, i, old_len) {
                    // Don't replace — this is an object key like {props: ...}
                    result.push_str(old_name);
                    i += old_len;
                    continue;
                }
                result.push_str(new_name);
                i += old_len;
                continue;
            }
        }
        result.push(chars[i]);
        i += 1;
    }

    result
}

/// Check if the identifier at position `pos` (length `len`) is in an object key position.
/// Object key position: preceded by `{` or `,` (ignoring whitespace) AND followed by `:`.
fn is_object_key_position(chars: &[char], pos: usize, len: usize) -> bool {
    // Check after: must be followed by `:` (ignoring whitespace)
    let mut after = pos + len;
    while after < chars.len() && (chars[after] == ' ' || chars[after] == '\t' || chars[after] == '\n' || chars[after] == '\r') {
        after += 1;
    }
    if after >= chars.len() || chars[after] != ':' {
        return false;
    }

    // Check before: must be preceded by `{`, `,`, or start of string (ignoring whitespace/newlines)
    if pos == 0 {
        return false; // Can't be object key at start of code (no enclosing {)
    }
    let mut before = pos - 1;
    loop {
        let c = chars[before];
        if c == ' ' || c == '\t' || c == '\n' || c == '\r' {
            if before == 0 { return false; }
            before -= 1;
        } else {
            break;
        }
    }
    matches!(chars[before], '{' | ',')
}
```

IMPORTANT: This heuristic is conservative — it only skips when we're confident it's an object
key. False negatives (failing to detect a key) are OK since they maintain current behavior.
False positives (skipping a non-key replacement) would be a bug.
